## 一、八个最可能被问的问题

### Q1「为什么冲突判定不走大模型？」

**答**：冲突判定是业务规则，必须**可复现、可审计、可追责**。LLM 判冲突有三个致命问题：
同一输入两次回答可能不同（不可复现）；判错了无法定位是提示词问题还是模型问题（不可审计）；
出事故后无法向客户解释"为什么系统说有冲突"（不可追责）。
所以时间窗重叠、装卸口占用、进撤场时长全部由规则引擎硬编码判定，LLM 只负责理解意图和组织语言。

**证据**：`src/admin/tools.py` 的 `check_conflict` 实现（纯规则，无 LLM 调用）；
`docs/09` 三层防线设计。

### Q2「怎么防止模型跳过校验直接建草稿？」

**答**：靠**服务端凭据强制**，不靠提示词求模型"请你先校验"。`check_missing_fields` 和
`check_conflict` 通过后才各签发一枚 JWT（HS256，绑定**草稿内容哈希** + 类型 + 5 分钟有效期）；
`create_schedule_draft` 必须同时携带两枚 token，服务端验证签名、类型、有效期、且两枚绑定
**同一份草稿哈希**——校验 A 提交 B 会被直接拒绝。提示词可以被绕过，服务端校验不能。

**证据**：`src/admin/tools.py` `_sign` / `_verify`（`JWT_SECRET`、`draft_hash` 绑定、
"疑似校验 A、提交 B，已拒绝"的拒绝理由）；评测用例 #20（以档案管理员身份直接建草稿）。

### Q3「人工确认之后，档期被别人占了怎么办？」

**答**：确认单不是"恢复即执行"。恢复执行时**强制重跑** `check_missing_fields` + `check_conflict`
双校验，冲突了照样拒绝创建。等待确认的窗口期被覆盖的风险由重检兜底。

**证据**：README「中断恢复演示」真实轨迹（确认后 check_missing_fields → check_conflict 复检 → 才创建）；
`docs/10` 中断恢复时序。

### Q4「RAG 为什么用 BM25 + 向量混合，不用纯向量？」

**答**：制度文档里有大量**精确口径词**——"装卸口 B"、"履约保证金"、编号类表述。纯向量检索对
这类词容易语义漂移（把"装卸口"召回成"物流通道"）；BM25 对精确词命中强但不懂同义改写。
两者用 RRF（k=60）融合，取长补短。切片 500 字，带"文档名/版本/切片号"溯源标记，
回答里的 `[来源N]` 能点回原文位置——因为**审计要求每一句结论可溯源**。

**证据**：`src/admin/rag.py`（`RRF_K = 60`、FAISS `IndexFlatIP`、无 faiss 自动降级 NumPy、
500 字切片）。追问"为什么 FAISS 全量重建不增量"：演示规模几十篇文档，重建毫秒级，
增量索引的复杂度收益为零——不为简历驱动的技术选型买单。

### Q5「评测 30/30 是怎么判分的，会不会自己给自己打分放水？」

**答**：四道关卡：①工具链必须是期望工具的**有序子序列**（允许多调只读工具，不允许跳步乱序）；
②期望关键词必须全部命中**回答正文**（已剔除固定页脚，防止页脚白送分）；③越权红线词
（"已锁定/已签约/保证可用"）扫描，但否定语境的引用不算；④期望建草稿的用例必须处于
`pending_confirm`，确认前真创建了直接 FAIL。陷阱题（制度里确实没写的停车费、安保比例、
保证金）期望回答是"未找到口径，请人工复核"——模型敢编数字就是最高等级风险。
另外把**链路模式**（plumbing，离线验证结构）和**语义模式**（semantic，接真实模型判内容）
拆开，mock 阶段只能过链路，不能谎称语义全对。

**证据**：`src/admin/eval/run_eval.py`（`overcommit_hits` 的否定词窗口、`is_subsequence`）；
`docs/11` 陷阱题选取原则；`docs/12` 实跑输出。

### Q6「LLM 供应商怎么切换的？锁定一家不怕涨价/停服？」

**答**：所有调用走 **OpenAI 兼容协议**，`LLM_PROVIDER` 一个环境变量在
`mock / openai / dashscope / deepseek / moonshot` 间切换，embedding 模型同机制可覆盖。
mock 模式离线可跑，让评测和演示不依赖外网与 Key。

**证据**：`src/admin/rag.py` 的 `PROVIDERS` 表；README 快速开始。

### Q7「为什么是'只读关联 + 草稿不生效'这么保守的方案？」

**答**：这是业务方三条硬约束决定的，不是技术胆小：①不做系统改造、不自动写回——现有
排期系统是生产系统，出错的代价远大于效率收益；②结论必须人工把关——AI 只能出候选提示，
"生效"这个动作只属于人，所以有 5 个人工确认门；③数据隐私与审计——字段级脱敏、
按角色授权（staff 建草稿服务端 403）、问答/工具轨迹/确认单全量留痕。
数智化转型的第一步是"辅助"而不是"替代"，这在 `docs/01` 业务挖掘阶段就定了。

**证据**：README 硬约束表；`docs/03` As-Is 的"3 个不可逆动作"；`docs/04` To-Be 的
"5 个人工确认门"；`src/admin/auth.py` RBAC。

### Q8「这个系统上线后怎么衡量有没有用？」

**答**：`docs/05` 报价单里就埋了验收方式：**30 样本回放验收**——拿真实历史排期样本回放，
对比人工核对耗时与冲突漏识别率。README「预期效果」表给了基线（单均 ~35 分钟）与试点目标
（~10 分钟复核），指标可量化而非"提升了体验"这种空话。系统侧还有 `agent-stats` 接口
持续输出工具调用频次、中断确认率等运行指标，试点期数据直接从审计表出。

**证据**：`docs/05` 验收条款；README 预期效果表；`src/admin/export.py` 统计聚合。

## 二、三个"如果被追问到底"的兜底

1. **「哪些部分是 AI 辅助做的？」**——如实答：文档起草与代码实现过程使用了 AI 辅助提高效率，
   但业务约束来自调研、架构与口径判定由本人定稿、全部评测与验证命令本人实跑
   （`docs/12` 留有真实输出）。**课程考察的是方法论闭环 + MVP 能力，把每个设计决策讲清楚
   就是最好的证明**——这正是本文档存在的目的。
2. **「如果给你三个月，下一个迭代做什么？」**——按路线图：v1.4 接真实 LLM 跑 semantic
   评测出对比报告（当前 mock 只能验链路，这点如实说，不吹）；v1.5 三源只读连接器，
   把"人工翻三处来源"真正自动化掉。
3. **「系统最大的短板是什么？」**——知识库质量依赖制度文档本身：制度写得模糊，AI 提示
   就模糊，这恰恰是"人工确认门"存在的原因；另外三源数据目前是演示种子，真实对接
   要处理增量同步与权限穿透（对应 v1.5）。**主动说短板比被问出短板得分高。**
