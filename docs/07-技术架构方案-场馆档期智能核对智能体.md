# 场馆档期智能核对智能体系统 —— 技术架构方案

> 版本：v0.1（方案稿，未含代码）
> 日期：2026-10-30
> 硬约束（全局红线）：
> ① 系统仅输出**冲突提示、缺项清单**，禁止自动锁档、自动签约、对外承诺容量；
> ② 所有正式结论必须**人工确认**；
> ③ 试点仅做源数据**只读**集成，不回写原有台账 / 服务台 / 文件库；
> ④ 全操作留痕，可审计追溯。

```
│  Web 工作台（按角色分发视图）                                  │
│   ├─ 一线服务专员工作台：档期查询 / 变更录入 / 冲突提示 /        │
│   │   缺项清单 / 复核留痕                                     │
│   ├─ 协调员工作台：版本管理 / 交接清单 / 未确认事项 / 责任归属   │
│   ├─ 审核与质量负责人控制台：样本管理 / 复核审计 / 试点启停 /    │
│   │   访问日志                                                │
│   ├─ 数字化工程师控制台：知识库维护 / 数据映射 / 只读同步配置    │
│   └─ 业务负责人控制台：试点范围 / 冲突裁决 / 口径审批            │
│  可选：企业微信/钉钉消息通知入口（仅推送，不承载写操作）          │
│  统一入口：HTTPS + API 网关 + JWT 鉴权 + 接口级权限校验          │
└──────────────────────────────┬──────────────────────────────┘
                               ▼
┌─────────────────────────── 服务层 ───────────────────────────┐
│  FastAPI（全异步）确定性业务服务，全部能力可脱离 LLM 独立运行：   │
│   ├─ 认证与 RBAC 服务（五角色权限矩阵）                        │
│   ├─ 档期管理服务：申请主表 / 版本快照 / 版本有效性判定          │
│   ├─ 变更管理服务：变更单录入、版本派生、双时间戳               │
│   ├─ 冲突检测服务（规则引擎）：时间窗 / 装卸口 / 进撤场时长       │
│   │   多维检测，输出"候选 + 依据 + 置信度"                     │
│   ├─ 缺项清单服务：必填字段校验 → 缺项生成 → 来源位置可点击      │
│   ├─ 人工复核服务：采纳/驳回/改值留痕，原值不可覆盖             │
│   ├─ 交接管理服务：交接清单、未确认事项跟踪、责任归属登记        │
│   ├─ 知识库管理服务：文档上传/切分/嵌入/版本/启停               │
│   ├─ 审计与日志服务：访问日志、复核审计、试点操作追溯            │
│   └─ 试点管控服务：试点范围开关、样本启停管控、口径审批状态机    │
└──────────────────────────────┬──────────────────────────────┘
                               ▼
┌─────────────────────── 智能体编排层 ─────────────────────────┐
│  Agent Orchestrator（编排核心，全部异步）：                    │
│   ① 意图识别 → ② 工具规划 → ③ 工具执行 → ④ 结果组装            │
│   → ⑤ 政策守门（Policy Guard）→ ⑥ 输出给人确认                 │
│                                                              │
│  ├─ 工具注册表（白名单机制，只读为默认）：                      │
│   │   检索制度知识库 / 查档期版本 / 跑冲突检测 / 生成缺项清单 /  │
│   │   查只读源数据快照 —— 不存在任何"写回/锁定/签约"工具        │
│   ├─ Policy Guard（硬约束的技术落点）：                        │
│   │   工具白名单过滤 + 输出内容审查（拦截"锁定/承诺容量/         │
│   │   自动签约"类表述）+ 敏感字段脱敏 + 强制引用来源             │
│   ├─ LLM 供应商抽象层（Adapter 模式，可替换）：                │
│   │   统一接口：chat / embed / rerank                          │
│   │   实现：OpenAI 兼容 / 通义千问 / 混元等，配置切换            │
│   ├─ RAG 管线：切分 → 嵌入 → 向量检索(pgvector) → 重排 →        │
│   │   引用组装（答案必须带文档出处，不可裸答）                  │
│   ├─ 溯源检索：档期样本 / 变更单 / 排期快照的结构化检索工具      │
│   └─ 人机确认门（Human-in-the-Loop）：                         │
│       LLM 产物一律标记为"候选"，落库正式结论必须经人工复核单      │
└──────────────────────────────┬──────────────────────────────┘
                               ▼
┌─────────────────────────── 数据模型层 ───────────────────────┐
│  ├─ PostgreSQL（业务主库）：用户/会话/档期/版本/冲突/复核/交接   │
│  ├─ pgvector 扩展（同库）：制度文档向量、检索元数据              │
│  ├─ 对象存储（MinIO/S3）：制度原文、排期快照文件、附件          │
│  ├─ Redis：会话缓存、接口限流、异步任务队列（arq/celery）       │
│  └─ 只读源数据适配器（试点红线落点）：                          │
│      台账 / 服务台 / 文件库 → 定时拉取 → 快照落地（双时间戳：    │
│      业务发生时间 + 系统接收时间）→ 只进不出，永不回写           │
└──────────────────────────────────────────────────────────────┘
```

**关键架构决策说明**

| 决策 | 理由 |
|---|---|
| LLM 与业务服务分离，冲突检测走规则引擎而非 LLM | 冲突判定是口径问题，必须可解释、可复现；LLM 只负责"解释与组装"，不负责"判定" |
| Policy Guard 独立成模块 | 三条硬约束不能靠提示词约束，必须做成工具白名单 + 输出过滤的代码级强制 |
| 版本快照不可变（append-only） | 支撑版本有效性判定与审计追溯，改值必走复核单 |
| 只读源适配器单向数据流 | "只读集成不回写"用架构保证（无写连接），而非约定 |

## 四、第一周最小验证目标（MVP-Week1）

**一句话目标：**
> 一名专员在 Web 工作台手工录入一份档期变更单，系统 30 秒内返回：冲突候选清单（含命中规则与依据）、缺项清单（含来源位置）、以及带文档引用的口径问答；专员可对每条候选"采纳/驳回/改值"并留痕。全程无任何自动写回外部系统。

**拆解为 5 个可验收里程碑：**

| # | 里程碑 | 验收标准 |
|---|---|---|
| 1 | 账号与权限骨架 | FastAPI + PostgreSQL + JWT 登录跑通；五角色权限矩阵生效（无权限接口返回 403） |
| 2 | 档期主流程 | 手工创建档期申请 → 生成 v1 快照 → 录入变更生成 v2（双时间戳、版本不可变可查） |
| 3 | 规则引擎冷启动 | 时间窗重叠 + 装卸口占用两条规则生效：两份样本档期导入后能检出 1 组冲突候选，evidence 可读 |
| 4 | RAG 问答闭环 | 上传 3~5 份制度/口径文档 → 切分嵌入入库 → 提问返回答案 + 文档出处（页码/章节），LLM 供应商可配置切换 |
| 5 | 复核留痕 + Policy Guard | 冲突候选逐条走复核单（原值保留、改值必填原因）；编写一个包含"自动锁定档期"字样的越权工具，验证被白名单拦截 |

**第一周明确不做：** 只读源同步（先手工导入样本）、候补/通知、报表、小程序；这些列入第二周之后。

**风险提示：**
1. 冲突判定口径必须由业务负责人在第 3 个里程碑前书面确认，否则规则引擎返工；
2. 嵌入模型一旦选定，向量维度不可中途更换（需重建索引），建议第一周就用正式供应商定稿；
3. Policy Guard 从第一天就写测试用例，硬约束不靠后期补。
