## 一、测试目标与范围

本方案验证 MVP 在五类场景下的行为是否与设计一致，重点不是“功能能点开”，而是三件事：
1. **写操作不可绕过人工**：任何创建/变更类动作都必须停在人工确认单上，未确认前不落库、不生效；
2. **拦截位置正确**：非法输入必须停在对应校验层（缺项层 / 冲突层 / 状态机层），不能越层执行；
3. **拒绝要显式**：越权与异常必须给出可机读的错误码，不能静默降级或返回 200 后什么都不做。

范围覆盖 4 个页面（登录 / 问答 / 草稿 / 审计）、12 个核心接口；不含性能压测与大模型语义质量评测（见第七节退出准则）。

## 二、测试策略与量化口径

| 维度 | 设计 |
|------|------|
| 分层 | 单元测试（纯逻辑）→ 接口级场景测试（本方案）→ 部署后线上冒烟（Test/06） |
| 用例设计 | 等价类 + 边界值 + 攻击面枚举；每条用例一个判定点，可独立复现 |
| 判定依据 | HTTP 状态码 + 响应关键字段 + 工具轨迹状态（ok/denied/blocked/pending_confirm） |
| 环境隔离 | 未登录、员工、管理员各自独立会话，禁止共享 Cookie（否则会把“已登录”误判成“未登录可访问”） |
| 数据基线 | `scripts/init_db.py` 重建：账号 3、知识库 6 篇 25 切片、已确认档期 3 条 |
| 通过标准 | 单条：全部断言命中；场景：通过率 100%；总体：无 P0/P1 缺陷遗留 |

## 九、遗留与后续

1. 性能基线：本轮只记录单请求耗时（毫秒级），未做并发压测；建议补 20/50 并发的 P95 与错误率。
2. 语义质量：当前 LLM_PROVIDER=mock，判定的是链路与风控，不是回答质量；接真实模型后需补语义评测集。
3. 故障演练：本轮故障场景为输入型异常；数据库断连、SSE 中断重连、确认单超时（真实时钟推进）尚未注入演练。
